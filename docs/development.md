# Development

[README.md](../README.md) says what ps1native is and how to build the app; [plan.md](../plan.md) has the design, the phases and the decision log; [AGENTS.md](../AGENTS.md) has the rules. This page is for working on ps1native itself: how it is built, tested and checked, and the house style.

## How it is built

| Part         | Where                                     | Built with                                                | State                                                                                                                                                         |
| ------------ | ----------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime      | `runtime/` (C)                            | compiled into the host                                    | Interpreter, memory/COP0, interrupts, timers, DMA, software GPU, GTE, SPU, MDEC, external CUE/BIN discs with CD audio, digital pads and memory-card protocols |
| BIOS         | `bios/openbios/`                          | built from nugget's source, then committed (its README)   | OpenBIOS with its shell, which boots in phase 1                                                                                                               |
| Presentation | `gfx/metal/` (Objective-C, Metal)         | host plus offline `.metallib`                             | Independent integer Metal rendering at 1×/2×/4× and frame presentation; software VRAM remains the console reference                                           |
| Mac host     | `shell/mac/` (C and Objective-C, AppKit)  | `make -C shell/mac` → `shell/mac/build/ps1native`         | Machine thread, Metal presentation, remappable keyboard pad, persistent cards and stereo Audio Queue output; headless inputs and PNG capture                  |
| Mac app      | `tools/mac_build.py`, `tools/pack_app.py` | `scripts/ps1native build disc.cue --platform mac-app`     | Native game app with a bundled local disc, or `make -C shell/mac app` for the launcher; ad-hoc signed with the hardened runtime                               |
| Recompiler   | `tools/` (Python)                         | run on the Mac: `python3 tools/codegen.py`                | Reads PS-X EXEs, decodes MIPS I, finds functions and blocks, and writes them as C the runtime runs natively, including captured code versions (phases 3–4)    |

There is no Xcode project for the Mac: plain Makefiles drive clang (`make -C <folder>`), and Python scripts pack what clang built, as in nxnative. Every host build also requires Xcode's Metal Toolchain (`xcodebuild -downloadComponent MetalToolchain` if missing), even with software rendering, to compile the offline metallib; no shader source is compiled on the device ([decision log](../plan.md#8-decision-log)). Beyond Xcode, that toolchain download and Python, nothing is installed. The iOS app (phase 7) will get its Xcode project generated (XcodeGen). Build outputs go to `build/` beside each Makefile, which git ignores.

The host is built for Apple silicon (`arm64`) and macOS 14 or later (`MINOS` in `shell/mac/Makefile`). `pack_app.py` reads the deployment target back from the host (`LC_BUILD_VERSION`) for `LSMinimumSystemVersion`, so the two cannot disagree, and signs the app with the hardened runtime: nothing is generated or mapped executable at run time ([plan.md](../plan.md#2-architecture), core rule). It replaces only an app it packed itself (the same bundle ID).

## Tests

Default tests need no game files, retail BIOS or GPU: they build their inputs in code or take them from [tests/ps1-tests](../tests/ps1-tests/README.md), and run the bundled OpenBIOS where they need a BIOS. They sit beside the code they test. The separate Metal comparison suite is the explicit GPU exception in [AGENTS.md](../AGENTS.md) and the [decision log](../plan.md#8-decision-log): it runs locally and in CI, reporting exit 77 from the test binary as skipped when no Metal device is available.

| What                                                               | Command                                                                  |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Runtime unit tests, and OpenBIOS booted to its shell (`t_boot`)    | `make -C runtime/tests run`                                              |
| The same under ASan and UBSan, in a build folder of their own      | `make -C runtime/tests asan`                                             |
| Mac host keyboard, replay, audio policy and saves                  | `make -C shell/mac/tests run`                                            |
| The same Mac host tests under ASan and UBSan                       | `make -C shell/mac/tests asan`                                           |
| Tool and script tests, the docs' links and AGENTS.md's length      | `python3 -m unittest discover -s tools/tests -v`                         |
| The app                                                            | `make -C shell/mac app && open shell/mac/build/ps1native.app`            |
| The host without a window: 300 frames, the last one's hash and PNG | `shell/mac/build/ps1native --headless --frames 300 --png /tmp/frame.png` |
| The same beside an interpreting machine, compared at block ends    | `shell/mac/build/ps1native --headless --frames 300 --lockstep`           |
| Metal reference comparison and higher-resolution geometry (GPU)    | `make -C gfx/metal/tests -j3 run`                                        |

A runtime C test (`runtime/tests/t_<what>.c`) includes `ps1.h` and links the whole runtime, built once into objects; it counts its checks with `CHECK`, prints `<what>: N checks, M failed` and exits non-zero on a failure; add it to `TESTS` in `runtime/tests/Makefile`. Mac host C tests live in `shell/mac/tests`, with the same check and summary conventions and their own Makefile; only `t_saves` needs to link the runtime. A Python test is a `unittest` file, `tools/tests/test_<what>.py`, whose docstring says what it checks. A `[RED]` line in a test's output is the runtime reporting what it does not model yet, not a failure. A PNG of a frame stays outside the repository; a frame is compared by its hash (`ps1_frame_hash`).

### Phase 2: hardware breadth

The host accepts `--disc /external/path/disc.cue` (or a single raw `.bin`). It opens the external files read-only and keeps them mounted across machine resets; it never packages or copies them. `t_disc` builds synthetic files in `/tmp` to test CUE addressing, multiple files and tracks, stored pregaps, validation and independent machines. `t_cdread` checks the controller ports, 75/150 Hz sector delivery, 2048/2340-byte FIFOs, BFRD data locking, DMA3 and Pause. `t_cdaudio` checks the commands' parameters, SetSession and GetQ, XA-ADPCM filtering and decoding, CD-DA Play with Report and AutoPause, the volume matrix and the SPU's CD input.

Supported CUE tracks use `MODE1/2352`, `MODE2/2352` or `AUDIO` in `BINARY` files, with `INDEX 00`/`01`. Other layouts, including synthesized `PREGAP`/`POSTGAP`, are rejected. A BIN lacks the SCEx string of the disc's wobble groove, which the drive checks, so the drive reads the licence string in sector 4 instead ([decision log](../plan.md#8-decision-log)): a licensed disc reads as on a console of its region, and a disc without one is refused, as by a console without a modchip. `scripts/disc_info.py <disc.cue>` prints what identifies a dump in its profile: the serial, the licence's region, and the SHA-256 of the boot executable and of each track, but never the dump's path.

`t_texture` covers 4/8/15-bit textures, CLUT and texture caches, affine polygons, windows/flips, modulation, transparency and masks. `t_gte` covers all documented commands, transfer side effects, overflow/saturation and the integer reciprocal. `t_spu` covers ADPCM/Gaussian interpolation, voices, ADSR, sweeps, noise, pitch modulation, reverb, capture and interrupts. `t_sio` sends complete digital-pad and memory-card transactions through the timed ports. `t_mdec` covers RLE, uploaded quantization/IDCT tables, pixel formats, FIFO backpressure and reordered DMA output. `t_timers` covers the counters' clocks, targets and IRQs, and their synchronization to hblanks and vblanks.

`t_ps1tests` runs 18 hardware test programs of [ps1-tests](../tests/ps1-tests/README.md), plan.md's homebrew test programs, under the bundled OpenBIOS: what a program prints must be the console's log, line for line, and the VRAM of a program that draws must hash as the console's picture does (`tools/ps1tests.py` hashes the picture, and shows where a dump of the runtime's VRAM differs). That README lists the programs left out, and why. `t_homebrew` adds three small programs built in code from MIPS encodings. All run in CI. This follows nxnative's separation of [synthetic CI tests](https://github.com/seedds/nxnative/blob/main/.github/workflows/tests.yml) from [local game bring-up evidence](https://github.com/seedds/nxnative/blob/main/docs/agents/README.md#checklist-for-a-new-title).

The [first game](../profiles/SLUS-01212/game.toml) reaches its title/main menu by the route in its profile: on 2026-10-30 with the runtime of commit 8680bf2, and again with a0d26af, to the same frame hash. Guest output is discarded during game validation; screenshots stay outside the repository and only frame hashes are recorded. Game validation is separate from CI, which needs no dump.

For a local headless route, `--input <frame>:<hex-buttons>` changes the port-1 active-high button mask at a zero-based presented-frame index and holds it until the next event. Repeat the option in frame order. For example, Start (bit 3) for six frames:

```sh
shell/mac/build/ps1native --disc /external/path/disc.cue --headless \
  --frames 2400 --input 1800:8 --input 1806:0 --png /tmp/frame.png
```

The window starts with the [keyboard mapping](../README.md#keyboard-controls): WASD for the digital D-pad and IJKL for the face buttons. [keys.h](../shell/mac/keys.h) maps AppKit characters to pad bits and tracks the original button by physical key code until release; `t_keyboard` checks defaults, reassignment, malformed preferences, shifted letters and release after remapping. [keyboard.m](../shell/mac/keyboard.m) provides the controls window and shared `org.ps1native` preferences. Headless replay files already contain pad masks, so keyboard changes do not change their inputs. Controller and card state belongs to each machine; product apps connect two persistent cards, while headless and developer runs leave them empty unless `--save-dir` is given ([Phase 5](#phase-5-the-mac-product)). SPU samples are drained on the machine thread; the Mac front end owns a separately locked playback ring, so its audio callback never accesses machine state.

Remaining gaps, each reported by a `[RED]` line when a program meets it: the CD-ROM's mechanical and seek timing, partial-sector overruns and sound-map XA-ADPCM; GPU drawing costs beyond the measured flat-rectangle fits (`[RED] gpu`), and FIFO/bus timing and CPU bus stalls within DMA packets (`[RED] dma`); GTE writes during a command; the SPU's sub-sample RAM, key-on and FIFO timing; MDEC's IDCT rounding and decode timing; which lines 480-line interlaced drawing leaves out, which psx-spx does not say; controllers other than the digital pad, and the serial link. The CPU counts each instruction's cycles ([cpu_ops.h](../runtime/cpu_ops.h)): one from the instruction cache, or a 32-bit read of its region where the code is uncached, a load's wait by region and width as ps1-tests' cpu/access-time measured them, and MULT and DIV running beside it. The cache's misses, a full write queue and memory control settings other than the BIOS's are not counted, so the ps1-tests programs that print times come within two cycles of the console's logs, not to them, and stay out of CI. Before phase 4, the first game twice sent a GPU list that came back on itself on its way to the title menu. The DMA completed whole lists inside the CPU's starting store, drawing each loop to an arbitrary packet limit without advancing guest time: the performance profile in phase 3 found the cost there. [Phase 4](#phase-4-overlays-and-profiles) schedules its packets instead, so the CPU can change or stop the list. Broader audible accuracy, hardware conformance and other games remain unverified; phase 6 records the local playback-delivery checks.

### Phase 3: the recompiler

`python3 tools/analyze.py <file.exe or disc.cue> [--profile profiles/<serial>/game.toml] [--list]` finds the functions and basic blocks of a PS-X EXE, or of the executable a disc boots: `tools/exe.py` reads the executable, `tools/mips.py` decodes each instruction as the interpreter runs it, and `tools/analyze.py` descends from the entry point through calls, branches and jumps, so data is never decoded as code. It follows a jump through a register when constants set the register (a BIOS call) or when the compiler's switch pattern names a table and its bound. What it cannot follow, it prints as a note, and goes to the interpreter at run time; a game's profile can name it in an `[analysis]` table: `functions` reached only through pointers, `jump_tables` (`{ jr = <address of the JR>, table = <address>, count = <entries> }`), and `data` ranges never to decode. On the ps1-tests programs, one to four jumps a program are left to run time: switch tables whose address the compiler kept on the stack, and calls through pointers. The tests (`test_mips`, `test_exe`, `test_analyze`) assemble their programs in code (`tools/tests/asm.py`).

`python3 tools/codegen.py <file.exe or disc.cue> --name <name> -o <build folder>/<name>.c` writes the native code of what the analysis found: a C function per guest function, entered at any of its blocks. Its instructions are the interpreter's own, one inline function each in [cpu_ops.h](../runtime/cpu_ops.h), called with each word and address as constants, so the delay slots, the load in flight and the cycles are the interpreter's by construction. The C goes to a build folder, never into the repository ([decision log](../plan.md#8-decision-log)). The dispatcher, `cpu_run` in [interp.c](../runtime/interp.c), runs native code where the machine has some for the code in memory ([native.c](../runtime/native.c) compares it word for word on each entry; a changed version selects its matching native entry, if captured in phase 4, or the interpreter), and the interpreter elsewhere and in a delay slot. Both take device events and interrupts only at the end of a block, after a delay slot or an exception, as the decision log has it; OpenBIOS still reaches its shell with the same picture, and every ps1-tests program still gives the console's result. `t_native` runs a program with each kind of instruction twice, interpreted and native, and compares the CPU, the cycles and memory at every stop: a wrong result or one cycle more fails it. The runtime's decoder and `tools/mips.py` must agree on every opcode, and `test_codegen` checks that every instruction the decoder names has its function in the runtime. Three ps1-tests programs, side-loaded under OpenBIOS in a scratch build, give the same cycles, output and VRAM with their native code as without, interpret 1 to 2% of their instructions (OpenBIOS's, until it is recompiled too), and run 1.8 to 6 times as fast.

The lockstep comparison, `ps1_lockstep_frame` in [lockstep.c](../runtime/lockstep.c), runs two machines from the same state, one interpreting and one with native code, and stops both at the same block ends: at every block, or at the first block end some cycles on, so that native code also goes from block to block by itself. It compares the CPU and the cycles at each stop, and memory and the devices at intervals and at the end of each frame. The first difference is reported by name, with the native block that ran last: for example `pc 80010188, native 00002628`, after the native block at `80010020`, when the native machine has gone into an exception handler the other has not. `t_lockstep` checks the report on native code written with a wrong register result and a wrong store, then runs four ps1-tests programs (`cpu/cop`, `gte/test-all`, `dma/otc-test`, `gpu/triangle`), whose native code the build generates, under OpenBIOS from reset in lockstep. An ADDIU of -87 for -88 in the native code of `gpu/triangle`, in a copy outside the repository, is reported at the stop where the two machines part.

OpenBIOS is recompiled too, in each build of the host and of the tests ([its page](../bios/openbios/README.md#as-native-code)). `tools/capture.c` runs it in the interpreter for 60 frames and keeps RAM and the addresses the CPU called or jumped to through a register, which `tools/codegen.py --bios --capture` analyzes beside the ROM. `t_lockstep` runs it from reset into its shell, 50 frames, in lockstep with the interpreter at every block: 6,504 of its 4,286,852 instructions are interpreted, and the ps1-tests programs, run with both their own native code and OpenBIOS's, interpret under 1% of theirs, but for `gte/test-all`, whose own jumps through registers no capture has given yet. The host runs OpenBIOS natively unless `--interpret` is given: 300 frames headless take 0.65 seconds instead of 1.31, to the same frame hash, and `--headless --lockstep` runs an interpreting machine beside it, comparing them at block ends 64 cycles apart and stopping at the first difference (exit code 3). The generated C of OpenBIOS is 1.6 MB; with every instruction inlined, clang instrumenting it for AddressSanitizer took minutes, so the sanitized build leaves the inlining to the compiler ([cpu_ops.h](../runtime/cpu_ops.h)), and `make -C runtime/tests asan` takes 76 seconds from clean at `-j3`.

`scripts/native_game.py <disc.cue> [--profile <game.toml>] [--frames <n>] [--input <frame>:<hex-buttons>]` makes a game native on the Mac it runs on, the last step of phase 3. It finds the profile by the serial in the boot executable's name and checks the executable's SHA-256 against it, then:

1. Builds the host and runs the profile's route with the game interpreted and `--capture` (OpenBIOS stays native, so the capture is the game's).
2. Generates the game's native code from the boot executable, the capture and the profile's `[analysis]` hints, split into files of about 20,000 instructions (`--max-ops`), and builds a host with it (`make -C shell/mac game`, into `shell/mac/build/game`).
3. Runs the route again in lockstep with an interpreting machine, which must agree to the end on the same frame hash, and times it natively and interpreted.

The capture, the generated C and that host hold the game's code: they stay in `shell/mac/build` (AGENTS.md: no game data). When the route no longer ends on the profile's hash, because the runtime has changed since the route was recorded, the script says so and keeps the last frame as `shell/mac/build/gen/route.png` to look at locally. On a disc built from `gpu/triangle` in a scratch folder:

- 79 addresses captured, 72 functions generated.
- The 900-frame route agrees in lockstep over 5,411,542 stops.
- 0.46% of instructions are interpreted, and the route runs in 1.6 seconds instead of 3.1.

That run also found two things, now fixed in the tools: the capture's RAM can hold long zeroed areas where a program ran before, which the analysis would decode as NOPs, so 64 zero words in a row end a run of code ([analyze.py](../tools/analyze.py)); and one C file for a whole program can exhaust the compiler's memory, so the C is split. `t_lockstep` builds `gpu/triangle` from four such files.

On the first game, Metal Slug X (USA), with its profile's route to the title menu and the runtime of commit 52cedd3, on 2026-10-30, the script met phase 3's exit criterion:

- 506 addresses captured; 723 functions and 7,788 blocks of native code, in four files.
- In lockstep the two machines agree to frame 2400, over 13,044,729 stops, on the profile's frame hash `a3d45a4b667b9f54`: the cycle model of phase 3 did not move the route's last frame.
- 4,655,433 of the route's 637,171,075 instructions are interpreted (0.73%).

The route takes 87.1 seconds natively and 90.4 interpreted, on the same Mac: native code takes 99.3% of the instructions off the interpreter, but only 4% off the time, 36 ms a frame on average where the console takes 16.7. A profile of the native host on the route says where the time goes. In the 20 seconds from 20 seconds in (macOS `sample`), the top of the stack is `plot` in 13,715 samples and `gpu_gp0` in 3,205, and no other function has five; the call graph puts both under the store in the game's native code (`game_f8007a4d0`) that starts the GPU's DMA. The CPU, the scheduler and the SPU did not run in those 20 seconds, so one transfer took them all: the GPU list of phase 2 that comes back on itself. The DMA runs a list whole the moment it starts, in none of the console's time ([dma.c](../runtime/dma.c)), and gives it up only after 100000h packets, so the loop, three packets of which one is a three-word drawing command, runs about 350,000 times while the CPU waits. On a console the CPU runs again after each packet of a list ([psx-spx, CPU Operation during DMA](https://psx-spx.consoledev.net/dmachannels/#cpu-operation-during-dma)) and the GPU draws at its own speed, so a list that loops is drawn only for as long as the game lets the channel run. At the end of phase 3, the open questions were:

- How much of the route the looping lists take, and so how fast native code is without them. Phase 2 saw the game send two; `scripts/native_game.py` shows only the host's own lines, so these runs did not show the `[RED] dma` lines.
- The fix, which belongs to the DMA's timing, one of phase 2's remaining gaps: a GPU list should take the console's time to run, with the CPU running beside it. If the game builds the loop because the runtime's DMA ends at once, as phase 2 suspected, it would then stop building it. psx-spx gives the DMA's rate, a cycle a word, but not the time the GPU takes to draw; the ps1-tests programs left out for their timing (`gpu/bandwidth`, `dma/chopping`, `dma/chain-looping`) come with the console's measurements. The limit of 100000h packets only keeps the runtime from hanging: lowering it would hide the cost, not remove its cause.

### Phase 4: overlays and profiles

The performance prerequisite is in [dma.c](../runtime/dma.c), at the cause measured above: a GPU linked list is now a scheduled stream of packets, taking a cycle per transferred word, with the CPU running between entries and also, incorrectly, during their transfer cycles: CPU bus stalls within packets remain unmodelled ([psx-spx, CPU Operation during DMA](https://psx-spx.consoledev.net/dmachannels/#cpu-operation-during-dma)). No packet-count guard drops repeated drawing. The CPU can change a future header, stop the channel or disable and re-enable it through DPCR; completion and IRQ3 arrive only after the final packet. `t_dma` checks a list containing repeated drawing, guest time, CPU edits, cancellation and DPCR pause/resume, beside the existing transfers and interrupt checks. The unchanged 2,400-frame title route took 83.5 seconds on the phase-3 native host and 19.3 seconds with scheduled packets on the same Mac, to the same hash `a3d45a4b667b9f54`. This removed the zero-time looping-list stall. Phase 6 adds measured flat-rectangle drawing waits; FIFO/bus timing and CPU bus stalls within a packet remain open and are reported by `[RED] dma`; other drawing costs are reported by `[RED] gpu` when a primitive or transfer executes through CPU GP0 writes or any DMA mode. Other channels retain their timing gaps. The console's cycle measurements in `gpu/bandwidth`, `dma/chopping` and `dma/chain-looping` are still outside CI; packet scheduling does not make those tests cycle-accurate.

Capturing final RAM alone loses an overlay overwritten before capture ends. [capture.c](../runtime/capture.c) now also writes `<out>.blocks`: the exact instruction bytes of every interpreted block version as it executes, deduplicated by address and bytes, with execution counts. [overlays.py](../tools/overlays.py) identifies each version by SHA-256 of its bytes; the code generator emits all observed versions, including several at one address, alongside static analysis of the final image. These are observed pieces of code, rather than guessed overlay file boundaries. Their full hashes distinguish the compiled functions; the runtime still compares every expected byte on entry, so a hash collision cannot run wrong code. Known versions can be overwritten and reloaded in either order, and unknown bytes go to the interpreter. A CPU store or synchronous DMA into the executing function returns immediately to the dispatcher, before its next instruction: entry checking alone would otherwise execute a stale constant. `t_overlays` exercises reloading, unseen bytes, exact capture contents, self-modification through a RAM mirror and DMA, and capture I/O failure under the sanitizers; `test_overlays` checks the content keys, malformed records and generation from transient versions absent from final RAM. All inputs are assembled in the tests.

`scripts/native_game.py <disc.cue> --route <table>` selects a profile route (`validation` by default). A route has `frames`, held `inputs` (`frame:hex-buttons`), and optional `pulses`: `{ start, stop, period, on, buttons }`, where the integer button mask is added for `on` frames every `period`, before `stop`. Base masks and overlapping pulses combine by OR ([replay.py](../tools/replay.py), `test_replay`; the host parser and its long files are checked by `t_replay`). The script writes an ordered input file once, used by capture, native playback, lockstep and timing. The host's `--input-file <file>` reads the same `frame:hex-buttons` format, one event per line; events remain ordered and the last mask is held. This replaces the 64-event limit for long gameplay routes. The script keeps all runtime `[RED]` lines, checks both timing runs' hashes as well as lockstep, and writes `game.survey.json` with addresses, hashes and counts into `shell/mac/build/gen` beside the capture. Native and interpreted instruction counts are printed by the host.

For an unknown game, `scripts/survey_game.py <disc.cue> --frames <n> [--input <frame>:<hex-buttons> ...]` needs no profile. It identifies the disc by its boot serial and executable hash, runs the supplied route with the game's code interpreted, and writes the capture, `survey.json`, `last.png` and a draft `game.toml` to `shell/mac/build/survey/<serial>`. The report lists code versions and addresses whose contents changed; it contains hashes and counts, not bytes. The draft labels the screen unverified: inspect the local picture and establish a route before copying its metadata into `profiles/`. Captures, generated C and pictures hold game data and stay local in ignored build folders.

The [first game's](../profiles/SLUS-01212/game.toml) `first_level` route runs from reset through Mission 1 to the prisoner-recapture results on 2026-10-30: 22,985 frames, 4,012 input events and five normal continues, with no patch or save state, ending on hash `a3d22ce034bdb516` at 320x240. The interpreter reproduces that clear, and the capture records 2,477 call/jump targets and 16,003 block versions; 19 addresses hold different code bytes during the route. Static analysis plus those versions generates 18,715 functions/blocks and 40,642 block entries in 13 C files. All 6,553,245,179 instructions run natively on the route and agree with the interpreter over 162,034,340 lockstep stops, including the results screen. The same route takes 70.6 seconds natively and 93.0 seconds entirely interpreted on this Mac, both to that hash; the route is about 384 seconds of console time. Phase 4 has met its exit criterion. To reproduce locally:

```sh
scripts/native_game.py /external/path/disc.cue --route first_level
```

The runtime suite passes plain and under ASan/UBSan with `DEVELOPER_DIR=/Library/Developer/CommandLineTools make -C runtime/tests B=build/clt -j3 asan`. The selected Xcode on this Mac has an older ASan runtime that hangs during shadow-memory initialization before `main` (confirmed with `sample`); using the newer Command Line Tools keeps that toolchain problem out of runtime changes. The Python suite, ruff, pyright and the app's build, hardened signature and headless OpenBIOS boot also pass.

### Phase 5: the Mac product

`scripts/ps1native build <disc.cue> --platform mac-app` ([mac_build.py](../tools/mac_build.py)) identifies the boot executable, verifies a known profile's hash and selects its `first_level` route, or `validation` if it has no first-level route. `--profile`, `--route`, `--frames` and repeatable `--input` override those choices. Unknown games need no profile and default to 2,400 frames; unobserved code keeps the interpreter fallback. Each invocation has an independent workspace under `shell/mac/build/products`, so a previous game's generated C cannot leak into a new build. It builds the capture host, captures exact interpreted block versions, generates and compiles the game, and requires a lockstep replay ending on the captured frame hash before packaging. Existing apps survive capture, compile or comparison failures.

The output defaults to `shell/mac/build/apps/<title>.app`, or `--output <path.app>` outside the repository. The signed Resources contain OpenBIOS and its licenses, `game.plist` and `disc/`: a normalized CUE sheet and one copy of each distinct source BIN. Shared-file track boundaries, stored pregaps and track modes survive normalization; source filenames cannot collide inside the bundle. The original dump is opened read-only. Apps, captures and generated game C contain game data and stay local; inside the checkout, game apps are accepted only under `shell/mac/build`. The packer uses its own unique staging directory and refuses resource/output overlap. The hardened arm64 executable needs no compiler, Python, original dump or checkout when played.

[product.m](../shell/mac/product.m) resolves a game's metadata and disc relative to its bundle, independent of the working directory. A generic `make -C shell/mac app` instead opens the launcher, with Open Game App and recent-game choices; building remains the command-line step. Game windows use the profile's title. Keyboard Controls (⌘,) remaps the digital pad, including arrow and function keys, unassignment and restoring defaults. Preferences use the shared `org.ps1native` suite across game bundle IDs; switching windows or leaving the app releases held keys.

[saves.c](../shell/mac/saves.c) connects two raw 128 KB cards under Application Support, located through Foundation's user-domain directory API. The namespace is `<serial>-<boot-sha256>` (or `homebrew-<hash>`), so rebuilding or moving an app keeps its cards, while a different executable gets its own. Only missing files are formatted; malformed, unreadable or symlinked images are refused. A session lock prevents concurrent copies from overwriting each other's cards. Dirty cards are written to unique temporary files, flushed and atomically renamed once per emulated second and before quitting; a failed write retains the dirty flag. AppKit requests termination, the machine thread finishes and flushes, then the main thread replies to the pending termination ([Apple, applicationShouldTerminate](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationshouldterminate(_:))). A final save failure cancels quitting and reports the error while keeping the machine alive for retry. `t_saves` checks creation, both slots, restart, locks, corrupt files, failed replacement and retry with synthetic cards.

Headless runs keep empty slots by default, including from a packaged app, preserving phases 3–4's acceptance routes. `--save-dir <directory>` explicitly enables persistence for headless and developer runs. Lockstep starts both machines with identical card contents, then compares their guest writes independently; its host flush happens after the comparison ends, and a divergence never flushes rejected card writes.

`test_mac_build` constructs synthetic CUE/BIN discs and profiles, checking track portability, shared files, pregaps, colliding source names, Mode 1, route selection and stable save identities. Its Mac integration test assembles its own GPU program into a bootable disc, builds a real app, renames the source disc away, then boots the bundled copy for 900 frames in lockstep: hash `a2fa0b6d358e04a3`, over 99% native. It verifies the hardened signature and persistent temporary cards across restart. No SDK or third-party test executable goes into this app. The controls window was also checked locally for remapping, preference reload and restoring defaults; closing the host window and ⌘Q both finish the machine thread. These checks need no retail game, retail BIOS or GPU in CI.

### Phase 6: the Metal renderer

[render.h](../runtime/render.h) defines an ordered, plain-C operation stream emitted by the software GPU before drawing: triangles, rectangles, lines, fills, copies, CPU uploads and cache/reset operations. The host hook belongs to each `ps1`, outside the compared console state. The existing software algorithms and CPU-visible VRAM remain canonical, preserving CPU reads, capture and native/interpreter lockstep. `t_render` checks emission order, complete packets, upload padding, snapshots, reset and two-machine isolation, and verifies that attaching a consumer leaves the software GPU byte-identical.

[renderer.m](../gfx/metal/renderer.m) owns independent native VRAM and texture/CLUT caches per machine. [renderer.metal](../gfx/metal/renderer.metal) rasterizes the operations with integer edge ownership, the reference's 12-bit truncated gradients, 15-bit blending, dithering, masks and ordered texture-cache effects. It also maintains separate 2×/4× VRAM for subpixel geometry; this state never changes the console's native VRAM. CPU uploads and copies preserve their wrapping and row order. Fills, untextured rectangles and untextured triangles run in parallel; Gouraud triangle gradients are prepared once before native and fine rasterization. Small, independent textured rectangles are batched in command order within a workgroup, with cache entries loaded by unique owners. Larger/windowed rectangles and textured triangles with independent source VRAM share four parallel passes: prepare gradients and cache events, find each texture slot's first miss and last requested tag over covered native pixels, shade pixels, then publish final cache contents. Triangles record observed native texels for the separate fine pass; event storage sits beyond the sample arrays. A triangle with no native coverage leaves the native caches untouched. Incoming stale bytes survive only until that slot's first miss, including when UV wrapping revisits an evicted tag. Texture-page or palette feedback retains the ordered fallback. This follows the reference's observable cache behavior rather than using floating-point Metal triangle interpolation.

Higher-resolution polygons interpolate at subpixels; sprite texels retain their native pixel footprint. Lines retain native width, packed 24-bit video is replicated from native scanout, and feedback regions use native pixel detail because they read the pixels being drawn in scanline order. Transparent or masked feedback writes preserve previous fine samples. Native VRAM and texture/CLUT caches are still computed independently and exactly. Retaining the CPU reference has a measurable cost; this phase does not claim to remove software rendering work or make every route faster.

`xcrun metal` and `metallib` compile `renderer.metal` and [display.metal](../gfx/metal/display.metal) into `gen/ps1gpu.metallib` during the Mac build. The app packer includes the library in Resources, and the host loads that binary with `newLibraryWithURL:error:`. No shader source is compiled while playing ([Apple's offline compilation workflow](https://developer.apple.com/documentation/metal/building-a-shader-library-by-precompiling-source-files)). Xcode's optional Metal Toolchain must be installed on the build Mac: `xcodebuild -downloadComponent MetalToolchain`. Software-only runtime tests need no toolchain component or GPU.

The Graphics menu selects software or Metal at 1×/2×/4× at frame boundaries; switching recreates the host renderer from the current console state without resetting the game or its saves. A build's `--renderer metal --scale 2` records an interactive default in `game.plist`; headless runs keep the software default unless explicitly overridden. The host accepts `--renderer software|metal`, `--scale 1|2|4`, `--verify-renderer` and `--shaders <offline.metallib>`. Verification compares the full native VRAM and persistent texture/CLUT caches each frame and exits nonzero at the first mismatch. Missing libraries, unavailable devices and GPU execution errors are reported explicitly. Initializing a missing Metal device from the menu keeps software rendering; a verification failure is never hidden by fallback.

The separate [GPU test suite](../gfx/metal/tests/t_renderer.m), `make -C gfx/metal/tests -j3 run`, requires a real Metal device and reports unavailable hardware explicitly. It compares full VRAM/cache contents and displayed frames, covering transfers, overlapping copies, texture depths/windows/flips, stale caches, palette promotion, self-feedback, masks/blending/dithering, display origins and 24-bit wrapping, PAL/interlace, partial packets, resets and independent machines. Higher-resolution tests count diagonal samples that differ from nearest-neighbor enlargement. Deterministic generated geometry stresses signed interpolation and clipping. CI also installs the Metal Toolchain when missing and runs this suite; exit 77 from the test binary means no device is available and is explicitly reported as skipped by `make run`.

## Continuous integration

`.github/workflows/tests.yml` runs on every pull request and push to `main`, on GitHub's `xcode-27` macOS image with Xcode 27.1 named by path in `DEVELOPER_DIR` (a new default Xcode on the image does not move CI): the runtime's and Mac host's unit tests, plain and under ASan and UBSan; the Metal comparisons (explicitly skipped when the test binary returns 77 for no device); the tool tests; and the Mac app, built, packed and checked (`plutil -lint`, `codesign --verify --strict`, the hardened runtime flag, `lipo -archs`), then run without a window from inside the bundle, which boots the OpenBIOS in its Resources. The runtime/Metal, tool-test and Mac-app jobs install Xcode's Metal Toolchain when missing before compiling the offline shaders.

`.github/workflows/lint-python.yml` runs ruff and pyright over the tools and scripts (configured in `pyproject.toml`), at the versions pinned in `.github/requirements/lint.txt`. Every finding fails the job: fix it, or silence it on its line (`# noqa: <rule>`, `# pyright: ignore[<rule>]`) with a reason. With the same versions locally, in a venv outside the repository:

```sh
python3 -m venv /path/to/lint-venv && /path/to/lint-venv/bin/pip install -r .github/requirements/lint.txt
/path/to/lint-venv/bin/python3 -m ruff check . && /path/to/lint-venv/bin/python3 -m pyright
```

Actions are pinned to commit SHAs, with the tag in a comment: a tag can be moved, a SHA cannot. Each job reads the repository only (`permissions: contents: read`), has a timeout, and is cancelled by a newer run of the same branch.

## House style

The code is dense and its comments carry the knowledge, as in nxnative:

- **Comments.** Each file starts with a comment on what it is, where it sits in plan.md, and the hardware facts it relies on, with their psx-spx section. A comment says what the code cannot: why, what was measured, what is still open; one short line where that is enough.
- **C** (the runtime and the hosts): C17 as clang builds it, free of warnings under `-Wall -Wextra`. Short names prefixed by their part (`mem_`, `front_`, `present_`), all machine state in the `ps1` struct ([AGENTS.md](../AGENTS.md)), several short statements on a line where they read as one step. Objective-C, with ARC, only where an Apple framework needs it (`shell/mac/front_mac.m`, `gfx/metal/`): the runtime is plain C, so iOS builds it unchanged.
- **Python** (the tools): the standard library first, and a package only for what it cannot do, under a permissive license; the MIPS decoder is the tools' own ([plan.md, decision log](../plan.md#8-decision-log)). A script takes its options with argparse, prints a line per step, and fails with `raise SystemExit(<the reason>)`. No formatter: ruff runs rules that find bugs, not style rules, and pyright checks types in basic mode.
- **Logs.** English, one line each, prefixed by their part (`host: `, `mem: `); a line that marks something unimplemented or wrong starts with `[RED] ` (`RED()` in the runtime).
- **Markdown.** A paragraph on one line, however long. A table's cells are padded so its columns line up, as prettier pads them, the separator row too; `tools/tests/test_docs.py` checks the links and anchors, not the padding.
